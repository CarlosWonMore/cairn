## ADDED Requirements

### Requirement: 提案的 MCP 入口

系统 SHALL 通过 MCP 暴露提案的生成与读取能力：`revision_propose` 与 `revision_list`。

两者 MUST NOT 提供应用能力；MUST 使用与本地入口同一份存储与校验实现。

读取 MUST 支持按状态（待审 / 已采纳 / 已拒绝 / 陈旧）与条数上限过滤。

读取返回 MUST 包含可供审阅的正文对照，MUST 标明提出者与提出时间。

#### Scenario: Agent 提出提案
- **WHEN** Agent 调用生成工具并给出目标记忆、拟改正文与理由
- **THEN** 系统保存提案并返回提案标识，记忆未改变

#### Scenario: 读取待审提案
- **WHEN** 调用读取工具并按状态过滤
- **THEN** 返回匹配的提案，含正文对照与元信息

#### Scenario: 工具面不含应用能力
- **WHEN** 列出可用的记忆治理类工具
- **THEN** 其中不存在任何可应用提案的工具

### Requirement: 提案在控制台可见

本地控制台 SHALL 展示提案列表与单张方案卡，并能跳转到对应的记忆与批注。

控制台中的「采纳/拒绝」若提供入口，MUST 与命令行使用同一校验与执行路径，MUST NOT 绕过版本一致性检查。

控制台 MUST 明确标示提案为「待人确认」，MUST NOT 让未采纳的提案看起来像已生效。

#### Scenario: 卡片可见且标注清楚
- **WHEN** 人打开控制台的提案视图
- **THEN** 能看到待审提案，明确标注「待确认」，并能看到改前改后对照

#### Scenario: 静态导出不含应用入口
- **WHEN** 导出只读静态页
- **THEN** 页面上没有任何可应用提案的控件
