# Design: 稳定的项目身份

## 上下文

用户要求按项目组织记忆，并给出了 projectId 的朴素构造方式（git URL / 绝对路径）。

代码现状（实测）：

- `src/store/schema.ts:15-20` 已有 `project(id, name, aliases, created_at)`，**`aliases` 字段全仓零引用**；
- `src/store/scopes.ts:45` 的 `ensureProject(projectId, name)` 是 `SELECT id FROM project WHERE id = ?` —— 直接用传入字符串当主键；
- `projectId` 从 MCP 的 `memory_add` / `memory_search` 等参数透传下来，没有格式校验。

所以「用路径当主键」在实现上是零成本的，但会在两个真实场景断链（proposal 已述）。本设计把预留的 `aliases` 用起来。

## 决策

### D1：id 用 UUIDv7，别名存 aliases

**选择**：新建项目时 `id = uuidv7()`，把传入的路径/URL 归一化后放进 `aliases` JSON 数组。

理由：

- UUID 与路径解耦，改名/换机器不影响归属；
- 复用现有 `uuidv7()`（`src/core/ids.ts`），与全仓其它主键一致；
- `aliases` 字段已存在，**不需要迁移**。

### D2：归一化规则必须可枚举、可测试

**选择**：只做下面这些**明确等价**的变换，不猜、不模糊匹配。

| 输入形态 | 归一化 |
|---|---|
| `https://Host/path/x.git` | 小写 host、去 `.git`、去凭据、保留 path 大小写 → `https://host/path/x` |
| `git@Host:org/repo.git` | 转成 `https://host/org/repo`（ssh 与 https 视为同一项目） |
| `ssh://git@host/org/repo.git` | 同上 |
| `D:\\Proj\\X\\` | 盘符大写、分隔符统一为 `/`、去尾部斜杠 → `D:/Proj/X` |
| `D:/proj/x` | 同上（**保留目录名大小写**，因为 Linux 上 `Proj` 与 `proj` 是不同目录） |

**为什么不统一小写整个路径**：在 Linux 上 `Proj` 与 `proj` 是两个不同目录，全小写会把两个项目合并。只在 Windows 盘符上统一大小写（盘符本身大小写等价）。

### D3：跨设备一致性——本变更的诚实边界

**这是本设计的薄弱点，必须写清楚。**

项目表**目前不同步**（同步链只覆盖 `personal-global` 空间的记忆事件）。因此：

| 情形 | 结果 |
|---|---|
| 设备 A 用路径 P 解析 → 建项目 X | A 上所有用 P 的记忆归到 X |
| 设备 B 用同一路径 P 解析 | **会再建一个新项目 Y**（B 看不到 A 的项目表） |
| 之后通过同步让记忆跨设备 | 记忆能同步，但**项目归属在两端不一致** |

**我不打算在本变更里解决它**，理由是：让项目表参与同步需要新增事件类型 + 冲突语义，属于独立的协议扩展；而现在**没有任何项目作用域的记忆**（库里只有 personal-global 与 device-local），所以这个不一致暂时不会造成实际损害。

**但必须让用户知道**：spec 的「同一项目在不同路径下解析」场景里，我加了**前提**「在别名已互相登记的前提下」。别名的互相登记，在当前阶段是**手工动作**（`project alias add`）。

### D4：别名冲突必须拒绝，不静默改绑

**选择**：追加别名时若该别名已属于别的项目 → 抛 `E_CONFLICT_STATE`，报告归属，不改任何数据。

理由：静默改绑会让「一批记忆突然换到另一个项目下」，且没有痕迹。拒绝并让人显式处理（先移除旧归属再追加）是唯一可审计的路径。

### D5：解析不校验路径存在性

**选择**：`project resolve` 不检查路径是否存在。

理由：正要跨设备用——B 设备上没有 A 的目录，但需要把同一项目的记忆归到一起。若强制存在性校验，别名机制就失去意义。

### D6：入口复用同一实现

**选择**：CLI 与 MCP 都调 `src/store/projects.ts` 导出的 `resolveProject()` / `listProjects()` / `addAlias()`。

理由：本项目已经吃过一次「同一判断写两份、改一份漏一份」的亏（`promotedPredicate` / `firstLine`）。这次从一开始就单点。

## 威胁模型

| 威胁 | 后果 | 缓解 |
|---|---|---|
| 归一化过度合并 | 两个不同项目被当成一个，记忆混在一起 | 只做可枚举等价变换；用例覆盖「`x` 与 `xy` 不得合并」「Linux 大小写敏感目录不得合并」 |
| 归一化不足 | 同一项目被建两次 | 可接受（多一个空项目，不影响记忆正确性）；用 `project alias add` 合并 |
| 别名被恶意改绑 | 记忆归属被悄悄换走 | D4 拒绝冲突；别名变更记审计 |
| 调用方传入子目录 | 建出一个「子项目」 | 不做自动上溯（不引入魔法）；文档要求传项目根 |

## 迁移与回滚

- **无 schema 迁移**：`aliases` 列已存在。
- 已存在的项目行（id 是普通字符串）**保持不动**；新逻辑只影响新建。
- 回滚代码后，UUID 形式的项目 id 仍是普通字符串，不影响读取。

## 可观测性

| 观察点 | 位置 |
|---|---|
| 项目数 / 别名数 | `cairn project list` 输出 |
| 新建 vs 命中 | `resolve` 返回值里的 `created` 布尔 |
| 别名追加 | 审计事件 `project` 类目 |
