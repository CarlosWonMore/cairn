# Design: 压缩后重注入

## 上下文

插件今天刚修好 `compaction/end` 的处理（清空去重集合 + 清空本会话累计），但那只解决"允许再次注入"，**没有解决"真的会再出来"**。

差别是实质性的：

| 只清去重（现状） | 主动重注入（本变更） |
|---|---|
| 下一条用户消息若命中该记忆 → 会重新注入 | 无论下一条消息说什么，**立刻**恢复 |
| 依赖关键词巧合 | 不依赖 |
| 用户问"继续刚才那个"→ 大概率失忆 | 原文仍在 |

meow-memory 的选择是后者，本变更对齐。

## 决策

### D1：追踪范围 = 注入过 + 经 MCP 读过/写过

**选择**：三类来源合并成一个会话内集合。

理由：只看"注入过"会漏掉一类关键场景——Agent 主动用 `memory_get` 查了一条记忆、基于它做了决策，然后压缩了。这条记忆没被"注入"，但它是决策依据，丢了就是灾难。

**实现**：插件已经在 `tools/post-execute` 钩子上留痕，在那里从工具参数里取 id 即可，不需要改 MCP 内核。

代价：`memory_search` 返回的是 preview 列表，参数里没有 id。**只处理 `memory_get` / `memory_add` / `memory_update` 这类带明确 id 的调用**；search 的结果不追踪。

### D2：重注入用独立预算，不挤占常规召回

**选择**：重注入单独限额，默认 `budgetBytes / 2`，通过 `reinjectBudgetRatio` 可调。

理由：如果重注入用满全部预算，下一步常规召回就没地方放了——用户会觉得"插件只记得旧东西"。留一半给新信息。

### D3：文本必须能区分来源

**选择**：重注入文本头用不同措辞（`以下记忆在本次会话中涉及过（上下文压缩后恢复，仅供参考）：`），不复用常规召回的 `以下记忆可能相关，仅供参照：`。

理由：模型对这两种文本的语义预期不同——前者是"你之前用过"，后者是"这可能与当前问题相关"。混用会让模型把旧上下文当成新证据。

### D4：内存 Map + LRU 上限

**选择**：上限 200 条，超出按访问顺序淘汰。

理由：追踪只在内存、不写盘。200 条 × 平均 100 字 ≈ 20 KB，可忽略。给死上限防止长会话无限累积（实测有个会话跑了 202 步）。

### D5：不依赖 compaction 事件的具体字段

**选择**：判 `type === 'compaction/end'` 且 `!data.error` 即触发。

已知风险：`data.error` 字段名来自 asar 里的类型定义，不同 DSH 版本可能变。**实现时 MUST 用可选链防御**：`evt.data?.error` 为真才跳过，字段不存在时按"成功"处理（宁可多重注入一次，也不要该恢复时不恢复）。

## 威胁模型

| 威胁 | 后果 | 缓解 |
|---|---|---|
| 重注入撑爆上下文 | 反而挤掉真实对话 | 独立预算 ≤ 总预算一半 |
| 无限累积 | 长会话内存增长 | LRU 上限 200 |
| 模型把旧记忆当新证据 | 错误的强相关判断 | 文本措辞明确区分来源 |
| 压缩事件字段变更 | 该恢复时没恢复 | 可选链 + 字段缺失按成功处理 |
| 跨会话串味 | A 的记忆出现在 B | 追踪集合按 sessionKey 隔离 |

## 迁移与回滚

- 无数据迁移（纯内存）。
- 回滚：`config.reinjectOnCompaction: false`（默认 true）。

## 可观测性

| 观察点 | 位置 |
|---|---|
| 上次重注入条数 | `/usage?debug=1` 的 diag 增加 `lastReinject` 字段 |
| 追踪集合大小 | 同上，`trackedCount` |
