# Design: push 前自动检查上行缺口

## 上下文

2026-11-12 任务 A 时发现一条记忆（`observed_at` 11-09、`created_at` 11-12 07:35）既无 `added` 审计也无上行任务。

**根因没查到**，但已排除三种猜测（见 proposal 的表格）。我不打算继续追——理由是：

1. 那次的命令现场**没有留下**（不在 `.cli-runs`、无 shell 历史记录）；
2. 影响面是 1 条记忆，且 `backfill` 已能补；
3. 真正值得改的不是「为什么漏了一条」，而是「**漏了没人知道**」。

## 决策

### D1：放在 push 前，不是定时，也不是 doctor 升格

**选择**：`syncPushCmd` 里先调 `findUpstreamGap`，有候选就打印警告。

理由：**push 是用户最关心「我的记忆上云了吗」的时刻**。在这个时刻暴露缺口，比让他记得去跑 `doctor` 有效得多。

**不升格为 doctor problems** 的理由：`upstreamGap > 0` 不等于库坏了。我们当初把 `problems` 定义为「库损坏/不可用」，`notes` 定义为「可自愈状态」。突破这个划分会让 `doctor` 退出码失去意义（CI 里会误报）。

### D2：提示但不阻断、不自动补

**选择**：打印警告后照常推送。

理由：

- **不阻断**：缺口不是推送失败的理由——已有的任务照推是对的；
- **不自动补**：`backfill` 会写 outbox（有副作用）。`push` 应该是一个「把已有任务发出去」的动作，不该静默改变队列。用户要补，跑 `backfill --apply` 是显式的。

### D3：复用 `findUpstreamGap`，不另写查询

**选择**：直接 import `src/sync/backfill.ts` 的 `findUpstreamGap`。

理由：这是本项目第三次强调同一条纪律——`promotedPredicate` 曾在 6 个文件各写一份，`firstLine` 曾两处各写一份，都出过 bug。缺口判定现在有 `doctor` / `backfill` / 本次 push 三个消费点，**必须共享同一实现**。

### D4：静默即健康

**选择**：缺口为零时不打印任何额外内容。

理由：如果每次 push 都打一行「缺口 0 条」，用户会很快无视它。**只在异常时说话**，提示才有重量。

## 威胁模型

| 威胁 | 后果 | 缓解 |
|---|---|---|
| 每次 push 多一次全表扫描 | 大库变慢 | 当前 57 条实测可忽略；`findUpstreamGap` 的 SQL 有 `NOT EXISTS` 与索引可用；将来上万条时再优化 |
| 提示被当成「已修复」 | 用户以为已补 | 文案必须明确「尚未入队，本次推送不包含」 |
| 三处口径漂移 | 数字对不上 | D3 强制复用同一函数，并加「三处口径一致」的规格场景 |

## 迁移与回滚

- 无数据库迁移。
- 回滚：删掉 `syncPushCmd` 里那几行即可；`push` 行为完全恢复到改前。

## 可观测性

| 观察点 | 位置 |
|---|---|
| 推送前缺口提示 | `cairn sync push` 的 stderr（`diag`） |
| 缺口数 | 与 `doctor` 的 `counts.upstreamGap`、`backfill` 的 `candidates` 同源 |
