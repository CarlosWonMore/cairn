# Proposal: push 前自动检查上行缺口

## Why

2026-11-12 任务 A 实测发现：库里有一条记忆（`01a1ceae…`，`created_at` 07:35）**既没有 `added` 审计、也没有 `sync_upstream` 任务**，因此不会上云。

已排除的猜测（都查过，有证据）：

| 猜测 | 证据 | 结论 |
|---|---|---|
| 从旧快照恢复 | 6 份快照（含当天 06:55 最新那份）**都不含**这条；06:55 快照 56 条、现在 57 条 | 排除 |
| sync pull 副作用 | 拉取侧零入队是设计要求；且该记忆 `observed_at` 是 11-09、`created_at` 是 11-12 | 排除 |
| 我的操作造成 | 缺口在 `sync push` 之前已存在（`backfill` 只读预演直接列出它） | 排除 |

**根因未定**。但**后果明确**：这条记忆差点永远不上云，而发现它的唯一途径是主动跑 `cairn doctor`，看 `notes` 里的一行提示。

## 真正的缺口不是「为什么漏了一条」，是「漏了没人知道」

`upstreamGap` 现在的设计是：

- 进 `doctor` 的 `notes`（一行提示）
- **不进 `problems`、不改退出码**
- 理由是「可自愈状态，不是库损坏」

这个理由本身成立，但**代价是它会被长期忽略**——这次就是靠主动查才发现，而不是它主动告诉你。

## What Changes

- **`cairn sync push` 在推送前做一次只读缺口检查**：发现候选就打印警告（条数 + 「这些记忆尚未入队，本次推送不包含它们」+ 指向 `sync backfill --apply`），然后**继续推送已有任务**。
- **不自动补**。补不补是人的决定——`backfill` 会写 outbox（有副作用），而 `push` 应当只是「把已有任务发出去」。
- **不改 `doctor` 的 severity**（仍为 `notes`、仍不改退出码）。

### 为什么是「提示」而不是「自动补」或「升格 problems」

| 方案 | 问题 |
|---|---|
| 自动补 | `push` 变成有写入副作用的命令；用户可能只是想推已有任务 |
| 升格 `problems` | `doctor` 退出码非零会让 CI/脚本失败，但「有记忆没上云」不等于「库坏了」——这是我们当初刻意区分的两条语义 |
| **提示** | 零副作用；在**用户最关心「上云了吗」的时刻**（推送时）暴露；不改变既有语义 |

### 明确不做的事

- 不自动执行 `backfill`；
- 不改 `doctor` 语义（`problems` / `notes` 的划分不动）；
- 不做定时检查（本项目同步退出会话关键路径，不装定时器）。

## Impact

- Affected specs: `cloud-sync`（推送前的可观测性）
- Affected code: `src/interfaces/app-service.ts` 的 `syncPushCmd`、复用 `src/sync/backfill.ts` 的 `findUpstreamGap`
- 无数据库迁移
- 回滚：移除 `syncPushCmd` 里那几行即可，推送行为完全恢复

## 风险与回滚

| 风险 | 处置 |
|---|---|
| 每次 push 多一次全表扫描 | 当前库 57 条，实测可忽略；`findUpstreamGap` 已被 `doctor` 与 `backfill` 复用 |
| 提示变成噪音让人无视 | 只在候选 > 0 时打印；健康时完全静默 |
| 用户误以为已补 | 文案必须明确「尚未入队，本次推送不包含它们」 |
