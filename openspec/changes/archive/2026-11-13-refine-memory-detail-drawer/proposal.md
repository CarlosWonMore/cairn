## Why

记忆列表里的「详情 / 修订史」当前是**整页替换**：点开时 `openDetail()` 直接 `clear(host)` 把列表干掉，换成详情内容；返回时 `render()` 重新走一遍 `/api/memories`。

实测（真实库 57 条，本机 Chrome）：

| 现象 | 实测值 |
|---|---|
| 点开详情 → 返回，`/api/memories` 请求次数 | **+2**（点开 1 次 + 返回 1 次） |
| 返回后滚动位置 | 2400 → **0**（回到顶部） |
| 详情本身可寻址吗 | **否**，地址始终是 `?view=memories&mode=brief`，刷新即丢失 |

三个后果：

1. **滚动位置丢失**：57 条记忆要往下翻十几屏才能找到目标，点开看一眼再返回就回到顶部，必须重新滚。
2. **重复请求**：每次进详情都重拉一遍列表，慢且没必要。
3. **刷新即丢**：正在看的详情刷新后消失；也无法把「这条记忆的详情」发给别人。

控制台里**已经有抽屉**（`openDrawer`，带 `role="dialog"`、焦点归还、Esc / 遮罩 / 按钮三个关闭入口、地址可寻址），导入视图的档案与批次就是用它打开的。记忆详情是**唯一还在用整页替换**的详情视图。

> 注：本次实测**没有观察到顺序变化**——返回后列表顺序与点开前逐条一致（`SAME_ORDER=true`）。用户报告的「展示顺序也会变动」可能与滚动位置丢失、或与筛选/搜索状态有关；本提案按**刷新即丢 + 滚动丢失 + 重复请求**三条可复现的问题立据，并在 tasks 里要求复现顺序问题再下结论。

## What Changes

- 「详情 / 修订史」改为**在抽屉里打开**，复用既有 `openDrawer`，不再整页替换、不再清空列表。
- 抽屉内容与现在的详情页一致：正文、meta 表、写下意见表单、批注列表、修订史。
- 抽屉状态**可寻址**：打开详情后地址带上该记忆标识（复用既有 `drawer` 键语义或新增 `mem`），刷新可复现，可分享。
- 返回/关闭后**列表不重新请求、不滚动**，因为列表 DOM 从未被销毁。
- 静态导出页同样在抽屉里打开详情，Behavior 一致。
- 冻结边界：不改 `/api/memories/:id` 返回形状，不改修订史数据结构，不改批注写入链路。

### New Capabilities

（无）

### Modified Capabilities

- `local-console`：只读预览视图的「查看单条记忆」要求改为以覆盖面板呈现且不销毁列表；查询与视图状态可恢复要求把「正在查看的记忆」纳入可寻址状态。

## Impact

- 代码：`src/interfaces/console/assets/ui-js.ts`（`openDetail` 改为 `openDrawer` 包裹；`go()` 与 `render()` 的抽屉收拢逻辑需覆盖记忆详情）、可能 `url-state.ts`（新增键）。
- 数据：无。
- 测试：`tests/console/render.test.ts`（源码级：详情走 openDrawer、不再 clear 列表）、`tests/console/url-state.test.ts`（新键往返）、`scripts/e2e-console-ui.mjs`（点开详情后列表仍在、请求数不增、滚动不回顶、刷新可复现、Esc/遮罩/按钮三入口）。
- 不影响：CLI / MCP / 检索 / 同步 / 治理链路。
