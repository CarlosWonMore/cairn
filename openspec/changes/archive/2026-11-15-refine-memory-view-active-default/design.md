## Context

2026-11-15 保管模式验证收尾时，用户在对端 webUI 看到 38 条已归档记忆与生效记忆混排，误判为「同步失败」。根因是展示层默认：记忆视图状态过滤缺省 = 全部状态。同步语义本身正确（迁出通知 → archived，审计保留）。

## Goals / Non-Goals

**Goals**
- 记忆视图默认只呈现需要关注的记忆（候选/生效/冲突），审计状态一键可选。
- 服务端执行默认过滤（检索纪律），静态页同构。
- URL 可回放：`status=all` 与显式状态值刷新/分享后复现。

**Non-Goals**
- 不改概览计数口径（全库审计数字）。
- 不改批注视图的状态过滤（它有独立语义）。
- 不改 `cairn export` 命令（其「活动内容 + 遗忘时间线」语义是导出契约，2026-11-15 已向用户澄清）。
- 不做「已归档批量清理」类操作（审计保留是规格要求）。

## Decisions

### D1：活动集 = candidate + active + conflicted

候选待审查、冲突待解决、生效在使用中——三者都需要关注。archived / tombstoned / superseded 是审计状态。单点常量 `LIVE_VIEW_STATUSES`（console/model.ts 导出），服务端路由与静态页 localFilter 同一出处。

### D2：默认过滤在服务端执行，静态页同构映射

`/api/memories` 的 status 语义扩展：**缺省 / 空值 → 活动集；`all` → 全部；逗号列表 → 精确**。选择服务端默认而不是客户端映射，因为「MUST NOT 用前端过滤伪造结果集」是既有规格纪律——默认视图的 total 与列表必须来自同一次服务端查询。静态页没有服务端，以内嵌模型做**同一映射**（同一常量），规格允许静态页零请求过滤。

### D3：URL 契约

`status` 键：缺省 → 活动视图；`all` → 全部状态；显式状态值 → 精确。旧地址 `status=archived` 等照旧回放。有意变更两处并记录：无参数从「全部」变「活动」、`?status=`（空值）从「全部」变「活动」——空值 URL 无既有使用方。

### D4：UI 只动状态下拉

首两项「活动视图（默认）」（value `''`）与「全部状态」（value `all`），其后是个体状态项（维持既有五项，不含 superseded——与现状一致）。qs() 不需要特判：`''` 缺省不写参数、`all`/个体值直传。

## Risks / Trade-offs

- **API 语义变更**：`/api/memories` 缺省从全部变活动集——该端点仅控制台自身与 e2e 脚本消费，随本变更同步调整；`status=all` 提供旧语义出口。
- **「候选要不要在默认视图」的口径**：候选是需要人处理的（晋升/拒绝），留在活动集；若未来嫌吵再议。
- **静态页与工作台默认一致**：静态导出常被当审计快照——但同一份 UI 代码服务两形态，分叉默认会造成「同一地址不同结果」；一致优先，用户可显式选全部状态。

## Migration

无数据迁移。发版后用户首次打开记忆视图即默认活动视图；旧分享链接带显式 status 值的照旧回放。
