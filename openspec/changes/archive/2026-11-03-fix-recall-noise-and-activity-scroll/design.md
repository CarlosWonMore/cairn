# Design

## 为什么是召回而不是面板

用户报的是「别的会话用过的记忆出现在这个会话」。先排除面板，避免改错地方：

| 检查 | 结果 |
|---|---|
| `GET /usage?session=bogus-id` | `{"status":"miss","sessionInjected":[],"recent":[]}` —— 未知会话返回空，不回落 |
| `GET /usage?session=<真实会话>` | 只返回该会话的环与累计集合 |
| 宿主侧会话键 | `payload.agent.id`；`Agent { readonly id: SessionId }`（api-catalog 实锤） |
| 客户端会话键 | `conversation.view` 声明 `scope: "session"`，`runInject` 把 `binding.key` 传给 `inject(sessionId)` |

面板没有串台路径。真正的问题在**查询构造**：`deriveQueries` 按「出现次数」取二字词，而中文里出现次数最高的二字词几乎全是虚词。

实测（真实库，只读检索）：

| 查询词 | 命中 |
|---|---|
| `是否` | 4 条，含「报告人非本人时不要询问是否关闭」「经验要沉淀到技能」 |
| `一个` | 「编写代码时必须遵循 ponytail skill」 |
| `这个` | 「Cairn 的投影预算是按宿主分级的」 |

这些记忆之间唯一的共性是含同一个虚词。它们一旦被注入，就会进入会话去重集合——**污染是持久的**：后面每一轮都不会再"重新判断"，因为 id 已经记成"注入过"。

## 三个选择

| 选择 | 方案 | 为什么不选另一个 |
|---|---|---|
| 怎么挡虚词 | **黑名单**（60 个明确的虚词二字组） | 白名单/词表要词性标注；按库内文档频率自适应又要一份统计与刷新策略，超出这次的范围 |
| 打分依据 | **命中的词在正文里真的出现**（大小写无关的包含判断） | 信检索内核给的分数：插件拿不到；按查询顺序：恰恰把最泛的词排最前 |
| 排序权重 | 强词 2 分（汉字 ≥3 或 ASCII 词）、实义二字词 1 分、虚词 0 分 | 只做过滤不排序：预算有限时仍会先塞泛词命中 |

## 为什么不做「相关性下限」

第一版试过「只被一个二字词命中就丢弃」，马上被既有用例打回：`帮我从记忆库里拉取一下记忆` 这条消息的实义词只有「记忆」，命中项正文也只含「记忆」——下限会把它误杀。

结论：**二字词不是天然不可靠，虚词才是**。所以判据放在"这个词是不是虚词"上，而不是"命中数够不够"。跨词边界的碎片（「们现」「在可」）留在查询里无害——它们在库里几乎不可能命中。

## 活动记录的滚动

宿主 CSS（`dsh-client-ui-conversation`）：

```css
.viewArea{flex:1;min-height:0;display:flex;flex-direction:column}
[data-phase=active] .viewArea{flex:1 0 auto;min-height:auto}
```

会话进行中视图区高度**不约束**，面板根节点的 `height:100%` 退化成内容高度，内部 `overflow:auto` 因此永远不触发——用户看到的是整个会话区在滚。

做法：列表加 `maxHeight: 56vh`。容器真给了确定高度时这个上限不起作用（flex 已经更矮），只有"高度自适应"那条路径才会用到它。仍然只有内联样式，不依赖样式表注入通道。

## 未验证

- 真实会话里的观感（列表边界、滚动条位置）需要重启宿主后肉眼确认。
- 60 个虚词覆盖的是本次实测 + 常见虚词；新的虚词型噪音只能靠再补名单，没有自动学习。
