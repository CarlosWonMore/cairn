# Design: 记忆重要度与使用信号

## Context

投影预算 1422 字节（2 KB 减去路由文案与受管标记），真实库 42 条 active、平均 818 字符——**只能装 6 条**。现有排序退化：`confidence` 只有三档（1.0/0.9/0.5）且 23 条并列，实际按 `updated_at` 与 `id` 排。

两个信号字段存在但空转：`last_used_at` 非空 0/45（`markUsed()` 零调用方）、`expires_at` 非空 0/45、`usage_count` 列不存在。

本变更的目标不是「更多记忆」，而是**让有限的 6 个名额给对的东西**，并给进不去的记忆一个体面的退场。

### 实测依据（2026-11-03）

| 数据 | 值 |
|---|---|
| active 条数 | 42（另有 candidate 3） |
| 总字符 / 平均 / 中位 | 34352 / 818 / 604 |
| 最长 4 条 | 3788、3376、2555、1656 |
| 装进 1422 字节能装几条 | 6 |
| `confidence` 分布 | 1.0×19、0.9×23、0.5×3 |
| `last_used_at` 非空 | 0 / 45 |
| 插件注入重复率（11-02 会话实测） | 202 次注入 / 6 种内容 = 97% 重复 |

## Goals / Non-Goals

**Goals**

1. 投影排序由「体积」改为「重要度 × 使用新鲜度」，且有地板防僵尸。
2. 重要度可被写入方表达（AI 判），受来源约束（推断不得自封高星）。
3. 使用信号分两层：被看到（`last_used_at`）与被要求（`usage_count`）。
4. 长期无用的记忆有确定归宿（归档，不删除）。

**Non-Goals**

- 不调用 LLM；不做内容蒸馏、语义合并、正文改写。
- 不引入向量 / 嵌入。
- 不改变 `confidence` 语义（它是可信度）。
- 不做 TTL 自动过期（`expires_at` 保持原样，本变更不用它）。

## Decisions

### D1：`importance` 与 `confidence` 必须是两个字段

**决策**：新增 `importance INTEGER`（1–5），不动 `confidence`。

**理由**：两者回答不同问题——
- `confidence`：这条内容**可不可信**（谁说的、有没有被确认）
- `importance`：这条内容**重不重要**（值不值得占预算名额）

现有数据证明它们正交：42 条里 `confidence=1.0` 的 19 条包含「Cairn 首条真实记忆」这类纪念性内容，也包含「记忆系统优先用 cairn MCP」这类硬约束——**可信度一样，重要度天差地别**。

把重要度塞进 `confidence` 会让它同时承担两种语义，之后既无法判断「1.0 是因为用户说的是事实」还是「1.0 是因为这条很重要」。

**取舍**：多一列、多一次迁移。可接受。

### D2：迁移用 `ALTER TABLE ADD COLUMN`，不重建表

**决策**：`ALTER TABLE memory ADD COLUMN importance INTEGER;` + `ADD COLUMN usage_count INTEGER NOT NULL DEFAULT 0;` + 建索引。

**理由**：004（`kind` 加 `lesson`）之所以必须重建整表，是因为 `kind` 受**硬编码 CHECK 约束**——SQLite 不支持修改列约束。而 `importance` / `usage_count` **没有 CHECK**（约束在应用层校验 1–5），新增可空列与带默认值的列都是 `ALTER TABLE` 的原生能力。

重建表的代价是实打实的：必须 `PRAGMA foreign_keys = OFF`（事务内设置是 no-op，必须事务前）、`PRAGMA legacy_alter_table = ON`（否则 RENAME 会把 8 个子表的外键改写指向 `memory_old`）、DROP 旧表、重建 6 个索引与 3 个 FTS 触发器。**这是全项目丢数据风险最高的操作，不该为两个可空列再付一次。**

**取舍**：没有 CHECK 约束，`importance` 的 1–5 边界靠应用层保证。可接受——写入路径只有 `addMemory` / `proposeCandidate` 两个入口，都在同一层校验。

### D3：`importance` 不进 `memory_revision`

**决策**：`memory_revision` 不加 `importance`。

**理由**：revision 记录的是**内容的历史**（正文、哈希、作用域、状态）。重要度是对「这条记忆整体」的顶层判断，随使用行为变化，**不属于任何一版内容**。现有 schema 已经遵循这个划分：`confidence` 也只在 `memory` 上，不在 `memory_revision` 上。

**推论**：修订内容不会重置重要度。这是对的——改个错别字不该让一条重要记忆掉星。

### D4：AI 可判重要度，但推断来源最高 3 星

**决策**：`memory_add` / `memory_propose` 接受 `importance`（1–5，缺省 3）；当 `authority === 'agent_inferred'` 时，上限强制为 3。

**理由**：AI 判重要度是必要的（人不会逐条标注），但**不受约束的自我判分会挤爆预算**——模型倾向于认为「我刚写的这条很重要」。给推断内容设 3 星上限，等于要求「想上 4/5 星必须有用户明确或确认的权威」。

**边界**：这是**上限钳制**，不是拒绝——`agent_inferred` 仍可正常写入，只是不能自封高星。

### D5：`last_used_at` 与 `usage_count` 语义分离，自动注入只写前者

**决策**：
- `memory_search` 返回命中 → 写 `last_used_at` + `usage_count += 1`
- 插件自动注入 → **只写 `last_used_at`**，不动 `usage_count`

**理由**（本设计最容易被忽略的一条）：插件是**每轮都注入**的。2026-11-02 实测：一个会话 202 次注入、去重后只有 6 种内容，**97% 是重复**。若自动注入计入 `usage_count`，那么「注入频率」而不是「真实需求」决定分数——被注入过的更容易被注入，正反馈死锁。

两者分开后：
- `last_used_at` 回答「最近被看到过吗」——注入和主动查都算，用于衰减判断
- `usage_count` 回答「被主动要过几次」——**只有显式检索才算**，这是高质量信号

**取舍**：自动注入的价值被低估了。但这恰恰是我们想要的——注入是插件的判断，不是用户的意图。

### D6：衰减必须带地板，否则等于给僵尸化上锁

**决策**：三重地板——
1. `importance >= 4` 豁免衰减
2. 本轮相关度 `>= 0.85 × 最高分` 豁免衰减
3. 绝对地板 `0.5`：任何记忆至少保留 50% 分

**理由**：纯衰减 = 马太效应。被注入过的分数高 → 更容易被注入 → 分数更高。一年后库里只剩少数「明星」，其余成为**存在于库中但不可见**的僵尸——这恰恰**加剧**了库膨胀（条目还在，可见性归零）。

三条地板的来源：
- ① 与 ② 照抄 `dsh-meow-memory`（`importance≥3` 或「超级匹配」豁免衰减）
- ③ 照抄 `dsh-prime-memory` 的 `max(0.5, 0.5^(天数/半衰期))`——原文注释写得很直白：「地板保证最多损失一半排序分，**长期事实不沉底**」

**为什么地板是 0.5 而不是 0.3**：0.5 意味着「最差情况也保留一半」，配合 `importance` 基线，一条 5 星记忆衰减到底仍是 2.5 分，仍高于 3 星新记忆的一半。若地板过低（如 0.1），5 星老记忆会输给 1 星新记忆，违背直觉。

### D7：归档而非删除，且必须留审计

**决策**：`importance = 1` 且超 180 天未使用 → `status='archived'`，记审计事件。

**理由**：`archived` 在 `memory-store` 里的既有语义就是「不活跃但仍保留」，用户重新记下同一件事是恢复意图。直接删除会破坏审计链且不可逆。

**判据取值**：`last_used_at` 优先，为 NULL 时回退 `created_at`。180 天来自「半年没碰过」的经验值，与 `docs/cairn-usage.md` 里的归档口径一致。

**不做**：不自动删除、不自动 tombstone（tombstone 是「明确退出」，归档是「不活跃」，语义不同）。

### D8：投影排序的分值合成

**决策**：

```
score = importance_adjusted × decay
其中 importance_adjusted = importance（NULL→3）
     decay = recencyWeight(days) ，但命中地板时 = 1
排序：lesson 优先 → score DESC → updated_at DESC → id ASC
```

`recencyWeight` 分桶照抄 `dsh-meow-memory` 的实现（<1d:1.0, <2d:0.9, <4d:0.8, <7d:0.65, <15d:0.5, <30d:0.35, <60d:0.25, <180d:0.15, ≥180d:0.08），再套 0.5 地板。

**为什么照抄而不是自创**：这套分桶是人家在真实使用中调出来的，且是纯函数、零依赖。自创一套没有依据。

**注意**：`selectProjectionCandidates` 目前是 SQL 排序（`ORDER BY ... confidence DESC`）。加入衰减后**部分计算需要当前时间**，两种实现：
- (a) SQL 里算：需要 `julianday` 运算，可读性差但能保持 SQL 排序
- (b) 取回候选后在 JS 里算并排序：`FETCH_CAP` 已有上限（400），数据量小，可读性好

**选 (b)**：与 `src/store/memories.ts:349` 附近既有做法一致（那里也是取回后过滤），且衰减规则将来要调时改 JS 比改 SQL 容易。**投影是低频操作（每会话一次），性能不敏感。**

### D9：DSH 插件必须同步改，且改动点只有三处

**决策**：`plugin/dsh/` 纳入本变更范围，改动限定在「调用参数 + 写入口径 + 面板摘要」三处，不动查询生成与注入逻辑。

**理由**：插件是注入的实际执行者。它用 `mcp__cairn__memory_search` 做召回——**和用户显式检索是同一个工具、同一个参数形状**。MCP 侧无法区分这两种调用，因此「自动注入不计 `usage_count`」这条纪律**必须由插件侧传参来实现**，否则不成立。

实测证据（2026-11-02 会话）：202 次注入、去重后 6 种内容、97% 重复。若注入计入 `usage_count`，这 6 条会因「被注入」而涨分，进而更容易被注入——**D5 要防的死锁会立刻发生**。

**三个改动点**：

1. `index.ts` 的 `searchOnce()`：`args` 加 `increment_usage: false`。两条执行路径共用该对象，一处改完两路生效。
2. `last_used_at` 的写入范围：**选 (i) 检索即写**——MCP 对返回集写。理由见 D10。
3. `usage-state.ts` + `/usage` 端点：补 `importance` 分布与 `usageCount` 汇总，只出摘要。

**不动的**：`deriveQueries`（每轮 ≤6 查询）、`createDedupeState`、`renderInjection` 预算、`makeInjectionMessage`（已带 `id`）。

**取舍**：插件与内核必须**同版本部署**。若插件先升级、MCP 不认 `increment_usage`，参数会被忽略——行为退化为「注入也计数」，即回到本变更要修的问题。**但这不会报错**，静默退化比报错更危险。缓解：MCP 侧未识别该参数时可选择记录一条 warn（实现时决定）。

### D10：`last_used_at` 用「检索即写」，不做回传确认

**决策**：MCP 在检索返回时，对**实际返回给调用方的集合**写 `last_used_at`；插件不额外回传「真正注入了哪几条」。

**理由**：

- `last_used_at` 是**弱信号**——它只决定衰减分桶，而分桶按天划分（<1d / <2d / <4d / <7d …）。检索返回 10 条、实际注入 3 条，那 7 条的误差最多让它晚一天进下一个桶，**不足以改变排序结论**。
- 回传确认需要新增一个 MCP 工具 + 一次往返 + 失败重试语义，收益（几条记忆的分桶边界）远小于成本。
- 更重要的是：**回传引入新的失败模式**——回传丢了，`last_used_at` 就永不更新，`usage_count` 反而更准，两条信号会不一致。

**取舍**：`last_used_at` 的精度略低于 `usage_count`。这是有意的非对称——一个信号求准（`usage_count`），一个信号求稳（`last_used_at`）。

### D11：插件改动必须真机验收，单测不算

**决策**：插件侧的验收标准是「重建 dist → 重载/重启 → 跑一轮 → 查库确认 `usage_count` 全 0 且 `last_used_at` 有值」。

**理由**：AGENTS.md 记录了两条已踩过的坑——
1. **改 `src/` 不重建 `dist` 等于没改**（插件从 `dist/index.js` 加载）
2. **重建了不重载也不生效**（2026-11-02 曾连续四轮误判「已重启但仍失败」，实际是取了最旧进程的启动时间）

本变更的验证点（`usage_count` 是否被误增）**恰好是「代码没生效时看不出来」的那类**：不生效 = 参数没传 = 计数照常增长 = 看起来「符合旧行为」。所以必须查到库里的实际值，不能只看测试绿。

**推论**：允许在实现阶段临时打开 `usage?debug=1` 探针确认新代码已进内存（AGENTS.md 提到 `renderProbe` 的做法）。

## Risks / Trade-offs

- **僵尸化仍在所难免** → 地板只能缓解，不能消除。真正的解是「让用户能看见沉底的记忆」，本变更不做（非目标）。
- **冷启动期只有 B 信号** → 前几周 `usage_count` 全 0、`last_used_at` 全 NULL，排序只剩 `importance` + `updated_at`。这比现状好（至少 `importance` 有语义），但要坦诚：**效果需要时间才显现**。
- **`markUsed` 回写时机在 MCP 侧** → MCP server 是独立进程，写库需要与插件连接共存。已确认 `node:sqlite` + WAL 模式支持多进程读写，但要**在实现时验证并发写不冲突**（tasks 2.4）。
- **自动归档会改变 `active` 计数** → 42 条里 `importance` 目前全是 NULL（视为 3），所以**本变更上线后不会立刻归档任何东西**。归档要等有人把某条调到 1 星。这是有意的渐进设计，不是缺陷。
- **`importance` 缺省 3 等于「没判」** → 大多数记忆会停在 3，排序退化为按时间。这是诚实的：AI 没给判断时，系统不该假装知道。

## Migration Plan

- 前进：`005_memory_importance_usage`，一次性，只加列 + 建索引。
- 兼容：旧版本打开新库——`schemaVersion > latest` 检查会拒绝，行为不变。
- 回滚：列可空（`importance`）或带默认值（`usage_count`），回滚到旧版后多余列被忽略，**不需要恢复备份**。这比 004 的重建表安全得多。
- 存量数据：`importance` 保持 NULL（代码里视为 3），**不做批量回填**——回填需要判断，而判断需要 LLM（本变更不做）。

## Open Questions

- 是否需要给控制台（`cairn ui`）加一个「重要度」筛选/排序？本变更只做 CLI 与 MCP。**建议延后**。
- `usage_count` 是否需要衰减（如只统计近 90 天）？**建议先不做**——加计数衰减会让语义变复杂，且冷启动期无意义。
- 归档的 180 天阈值是否需要可配置？**建议先硬编码**，等真有需求再抽配置。
